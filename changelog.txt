== Changelog ==

= 1.0.7 2026-09-25 =
* Added - The build now checks the plugin's declared compatibility on every change. The minimum WordPress and PHP versions are stated in four places (the plugin header, readme.txt, README.md and the lint configuration) and nothing kept them equal, so the copy a merchant reads could drift from the copy the installer checks. A mismatch now fails the build.
* Fixed - The plugin's minimum WordPress and PHP versions are now declared in the plugin header as well as readme.txt. WordPress reads the header to decide whether a site may install or update at all; before this it read only readme.txt, so an unsupported site was never stopped and the requirement shown on the plugin page came from the other file.
* Added - The build checks that every screenshot the readme names actually ships (a declared screenshot with no image makes the plugin page serve a 404), that the readme describes only the release being installed, and that the version number agrees in every file that carries it.
* Changed - The compatibility lint is now a real gate in CI. It ran with its result discarded, so it could not fail a build and any finding it made was invisible.

= 1.0.6 2026-09-24 =
* Fixed - The subscriptions screen printed a PHP warning into every healthy subscription's Actions column ("Undefined variable $frm_chip_who"). The payer string used to build each control's accessible name was defined inside the "Retry now" branch and read again in the "Renew now" branch, so every subscription with nothing owed — the common case — rendered the notice on the merchant's screen. It is now resolved once, above the branch, and each row keeps a distinct accessible name.

= 1.0.5 2026-09-16 =
* Fixed - Every paid submission logged PHP warnings from the form plugin ("Undefined array key success_url" and two more) and passed an empty value where PHP 8.1+ expects a string. This happened when the form's own confirmation was left on the default message: sending the payer to the payment page then made the form plugin read redirect settings the form never had. The missing settings are now supplied, so a paid submission logs nothing.

= 1.0.4 2026-09-16 =
* Fixed - If the payment action read the payer's email or name from a field that was left empty, the whole purchase failed with a message from the payment gateway naming a field the payer could not see, and no indication of where to fix it. The details are now checked before the payment is created, and the message names the field by its label, the form it belongs to, and where the mapping can be changed.

= 1.0.3 2026-09-13 =
* Fixed - "Retry now" was offered on every subscription that was not cancelled, including a healthy one with weeks left in its paid period. Pressing it charged the payer early and moved every later charge forward, so a subscription paid until November could be billed again and then owe from December. The two actions are now separate: Retry now collects a payment that is actually owed and never changes the schedule, while Renew now charges the next period early and says so.

= 1.0.2 2026-09-13 =
* Fixed - A refund left the subscription it belonged to running, with no record that money had been returned. The refund is now recorded against the subscription and shown on the subscriptions screen next to the next charge, so a payer is not charged again for a period that was refunded without the merchant being able to see it.
* Added - Refunding a payment that funds a subscription now offers the choice of refunding only, which leaves the subscription running, or refunding and cancelling it. The cancel is only sent after the refund succeeds, so a refund that fails cannot leave a subscription ended for nothing.
* Fixed - A negative amount in the payment action was charged as its positive value. The amount is now refused before that can happen, with the same message as any other unusable amount.
* Fixed - A currency other than MYR could be selected on a CHIP action and was replaced with MYR on save without explanation. The choice is now shown as fixed to MYR, with the reason stated, so it is never offered as an option that will be discarded.
* Fixed - A renewal that ran late moved the subscription's billing day forward by however late it ran, permanently, so a payer billed on the 10th could end up billed on the 13th. The next period is now counted from the date the payment was due, and the billing day stays as the payer agreed.
* Fixed - The subscriptions screen did not match Formidable's own admin screens: it rendered without the Formidable header and at WordPress's default heading size. It now uses Formidable's page shell, so it looks like part of the plugin rather than a separate page.
* Fixed - The refund options were hidden on any payment without a recorded card type, which included payments confirmed by CHIP's callback rather than the browser. The options now appear for every payment that funds a subscription.

= 1.0.1 2026-09-13 =
* Fixed - A purchase paid for less than the order completed the payment as if paid in full. The amount CHIP reports is now compared with the order total, and an underpayment is held as pending with the amounts recorded instead of being marked complete.
* Fixed - A field inside an embedded form (Formidable Pro) could be selected in the field mapping but its value could not be read, so a form using one for the payer's email or phone could not take a payment at all. The value is now resolved from the embedded form's own entry.
* Fixed - A CHIP outage was treated as a failed charge attempt, consuming one of the four retry slots and moving the subscription's bill date forward. A timeout, a 5xx or an unreadable response now defers the renewal instead, and only a decline that names the card counts against the retry limit.
* Fixed - The renewal run loaded every due subscription and charged them one at a time, so a store with many falling due on the same day lost the request part-way and silently skipped the rest until the next run. The run is now bounded and reports what it deferred.
* Fixed - A subscription with no stored card could never be charged, and because its due date was already in the past it was always first in line. It now stands down so it cannot block subscriptions that can be charged.
* Fixed - The renewal run reported its remainder by subtracting the rows it had touched, so a subscription skipped because another worker held its charge lock was counted as done and the run claimed there was nothing left. The remainder now reflects what is really still due.
* Fixed - A subscription that failed in place could be left with no renewal schedule on a site that updated the plugin rather than reactivating it. The schedule is now asserted on every request.
* Fixed - The payments screen offered a manual retry only when a failure had already been recorded, contradicting the subscriptions screen, and a healthy subscription showed no action at all. Both screens now offer a retry unless the payer has ended the subscription.
* Fixed - A subscription with a completed payment could not be found by a payer replacing their card, and the emailed card-update link created its checkout up front so it was spent before it was opened. The link is now stable and opens a fresh checkout when used.
* Added - A CHIP Subscriptions screen listing every subscription with its renewal state, attempts remaining, and a Retry now action.
* Added - Renewal failure emails to both the merchant and the payer, with a link for the payer to supply a new card without logging in.
* Added - Retrying is capped at the card network limit of 15 charge attempts per card per 30 days, and at 10 consecutive failures.
* Added - Signature verified server callbacks with an API fallback, and per-payment locking so the return redirect and the server callback cannot settle the same payment twice.
* Changed - The retry control names the payer and the subscription, the subscription table uses row headers, and the outcome of a retry is announced to assistive technology.
* Changed - The subscription list is paged so a long list does not load every subscription in one request.

= 1.0.0 2026-09-11 =
* Added - CHIP registered as a payment gateway on Formidable's shared Collect a Payment action, alongside Stripe, Square and PayPal.
* Added - One-time payments through the CHIP hosted checkout.
* Added - Recurring payments, charged from the site on a schedule using a card token stored by CHIP.
* Added - Failed renewal retries on days 3, 5 and 7 after the due date; a rejected card token fails the subscription immediately rather than retrying.
* Added - The payments screen shows a subscription's next charge, any retry in progress, and why a renewal failed, with a Retry now action.
* Added - Payment method selection, configured globally and overridable per form.
* Added - Runtime resolution of the DuitNow QR and ShopeePay identifier groups against the methods the brand actually has.
* Added - Phone as a mappable client field, sent to CHIP exactly as the payer typed it.
* Added - Fields inside an embedded form (Formidable Pro) are offered in the field mapping, labelled with their form.
* Added - Refunds from the Formidable payments screen.
* Added - Subscription cancellation, which removes the reusable token and stops future charges.
* Added - Global settings section for credentials, purchase defaults and the payment method list.
* Added - Filters: `frm_chip_purchase_params`, `frm_chip_return_url`, `frm_chip_purchase_timezone`, `frm_chip_action_field_options`, `frm_chip_sslverify`.
* Changed - Validation errors from CHIP are reported with the field and reason instead of a generic HTTP status.
